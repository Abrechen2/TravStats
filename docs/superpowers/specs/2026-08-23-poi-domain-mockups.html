POI Domain — Places, Lists & Checklists

A place you have been to becomes a first-class thing in TravStats: collectable into your own lists, tickable off shipped checklists with photo proof, and drawn on the globe whether or not it belongs to a trip.

2026-08-23 domain key · poi closes #177 spec: 2026-08-23-poi-domain-design.md status: awaiting 3 decisions
Two conventions this page follows. Annotations and structure are English per the repo policy; every string inside a mockup is German, because that is user-facing copy — the English mirror ships in the same change. And the chrome is the product's real one: Syne for display, Inter for text, IBM Plex Mono for data, the luggage-tag mark, the amber accent. Teal is the POI domain colour and appears only on domain surfaces — pins, legends, badges — never on app chrome. That separation is itself part of the design.

01The decision everything hangs from

Issue #177 does not just request a feature, it fixes the architecture.

“May this could be resolved on adding the global POI feature. I think they have to be synced because otherwise there will be two different kinds of POI which would be very confusing.”

— #177, Option to show POIs of trips on the dashboard map (open)

Today a POI is a TripStop with domain: "poi" — it exists only as an attachment to a trip. Two ways forward:

OptionWhat it costsWhy it fails / holds
(a) Draw trip stops on the global map ~2 days A place only exists if it has a trip, so “every McDonald’s worldwide” is inexpressible. The same restaurant on two trips is two unrelated rows that no count can reconcile. Dead end.
(b) Promote the place; the trip becomes a view of it a migration of live data The only shape the owner’s brief is expressible in — and the exact split Lodging/LodgingStay already ships. Chosen.
Option (a) is not a cheaper version of (b). It is a detour that has to be undone — building the brief later means doing (b) anyway, on top of more data.

The model, in one line each

Lodging ──< LodgingStay >── Trip // shipped, reviewed, understood
Place ──< PlaceVisit >── Trip // this plan, mirrored 1:1
Place >──< PlaceList // your own lists — many-to-many
CuratedPlace ··> Place // materialised only when you tick it
EntityAnswersNote
PlaceWhat is this thing, and is it in my logbook or on my wishlist?Per-user. lat/lon required — drawing is the point.
PlaceVisitWhen was I there, on which trip?Carries a time, not just a date — that is #175, for free.
PlaceListWhich collection does it belong to?Many-to-many: a Maccis can be in “Maccis” and “Rom”.
CuratedPlaceWhat are the targets on a shipped checklist?Global, seeded from CSV like Port/Ship. Not a pin until ticked.
Place.visited defaults to false — deliberately the opposite of Lodging.visited. Lodging chose true because every row predating the column was a real stay. Here the dominant creation path is adding a target to a list, and a wishlist entry silently counted as visited would inflate the headline number on day one. Counts follow the shipped rule: from data and dates, never a status string — a visit dated next month is not a visit.

The migration, and the three ways to lose data

TrapHandling
TripStop is not POI-only It also carries hotel, train, hike, null. Only domain='poi' moves; TripStop survives as the generic timeline primitive.
Coordinate-less POI stops TripStop.lat/lon are nullable, Place.lat/lon are not. Those rows are neither migrated nor deleted — they stay trip stops. Deleting user text to satisfy a schema is not an option.
The DELETE is irreversible Expand/contract: the copy ships one release before the delete, so a bad backfill is recoverable from rows still present.
#175 and #176 are already-shipped behaviour (time ordering, map labels) and a rewrite is free to drop them silently. Both get a test naming the issue number.

04Colour findings — computed, not eyeballed

Two encoding rules below are measurements, not taste. Both changed the design.

Map pins are a scatter case: any two categories can end up adjacent, so every pair must separate, not just neighbouring ones. Running the shipped domain palette against that bar, on the dark surface: 

$ validate_palette.js "#f0a947,#6fa0d6,#d4778f,#5ec2b2" --mode dark --surface #0d1117 --pairs all

  [WARN] CVD separation        worst #5ec2b2↔#d4778f  ΔE 6.8 (deutan)
  [FAIL] Normal-vision floor   worst #5ec2b2↔#6fa0d6  ΔE 12.4 — below the 15 floor
  [PASS] Contrast vs surface   all 4 ≥ 3:1
Finding 1 — POI teal and cruise blue are the hardest pair in the product. ΔE 12.4 for normal colour vision, below the floor of 15. On the All tab, place dots would sit beside cruise-port dots: same mark, near-same hue. So a place pin there carries a distinct glyph, and the existing label pass is doing load-bearing work, not decoration. This is not a request to repaint the brand — those hexes are canonical in BRAND.md and shared with TravStatsWeb — it is a constraint on how the new layer is drawn.
Finding 2 — “colour by category” cannot work on a map. Only the first three slots of a categorical palette clear the all-pairs floors. Seven place categories cannot be seven hues. Category is therefore encoded as the pin's icon (🍟 🏛 🌲 🖼), which also survives greyscale, print and forced-colours. Ghost targets are hollow and dashed because #5ec2b2 vs. muted grey measures ΔE 12.7 — also below the floor. Shape carries it; colour merely agrees.

The one palette that does pass all-pairs cleanly is a small fixed set — so the list-colour picker offers validated slots in a fixed order rather than a free colour wheel, which guarantees nothing: 

$ validate_palette.js "#3987e5,#d95926,#199e70" --mode dark --surface #161b22 --pairs all

  [PASS] Chroma floor          all 3 ≥ 0.1
  [PASS] CVD separation        worst ΔE 9.4 (deutan)
  [PASS] Normal-vision floor   worst ΔE 20.9
  [PASS] Contrast vs surface   all 3 ≥ 3:1
  → ALL CHECKS PASS

Past three lists on screen at once, identity comes from the legend and direct labels — which the pin layer already implements via pickLabelled — or the view folds to “Other”.

Each phase is releasable. Branch dev/poi-domain off main; no VERSION/CHANGELOG edits on the branch — those belong to /deploy.

Models + the §03 migration + CRUD + Zod + place picker + placePinsLayer + colour store & legend + the real POI tab + place-visit in the trip timeline + domain available: true + un-gate poiDashboardTab. Closes #177 on its own.

CSV / Google Takeout / Maps saved places via ImportBatch; place suggestions from trip-photo EXIF (TripPhoto.lat/lon is already populated). Own spec — not promised here.

The brief needs A + B + C. Phase A alone already delivers a working domain and closes the open issue, so it is a legitimate stopping point if priorities move.

06Three decisions for the owner

Everything above is settled except these.

#QuestionRecommendation & why it matters
1 Lazy materialisation vs. copy-on-subscribe for checklists Lazy — because of the lists that come next. UNESCO (~1200 sites), national parks, Michelin stars: copy-on-subscribe hands every subscriber a full catalog they mostly have not visited, and a coordinate corrected in 2.9 never reaches anyone who subscribed in 2.8. Cost of lazy: the one screen in mockup 4 that renders two kinds of row. Hard to reverse once Phase C ships — it changes what the user's own rows mean. Worth settling before C starts, not during.
2 Which checklists ship in v1? The two seven-item wonder lists only (New 7 + Ancient 7). Enough to prove the mechanism without curating a 1200-row CSV nobody has asked for. Anything bulk-derived needs a licence line first — OSM extracts are ODbL, a hand-curated 7-row CSV is not.
3 Standalone places, or trip-only? Standalone with an optional trip, like flights and lodging. This is the assumption that makes “every McDonald’s, worldwide” possible without inventing fake trips — confirm it, because everything else rests on it.
Not a decision, a flag. Phase A migrates live user data. It should run on the RC server against a prod mirror (scripts/stage-rc-from-prod.sh, CT 107) before it goes anywhere near production. The expand/contract split in §03 exists so a mistake there is recoverable rather than final.
